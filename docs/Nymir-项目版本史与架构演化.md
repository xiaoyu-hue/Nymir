## 3. V1：GitHub 建仓前的早期阶段

### 3.1 阶段定位

V1 是 Nymir 最早期的发展阶段。

这一阶段发生在 GitHub 仓库建立之前，因此不存在对应的公开 GitHub 提交记录。

这一阶段的主要意义是：

> 从一个最初的想法逐渐形成可以运行、可以验证的项目雏形。

### 3.2 项目状态

V1 的主要特征：

- 项目处于早期开发阶段
- GitHub 仓库尚未建立
- 代码与开发过程主要处于仓库建立之前的阶段
- 重点是产品概念与基础功能探索
- 架构尚未完全稳定

因此，V1 更适合被理解为：

> Nymir 的项目史前期 / 原型阶段

而不是一个可以通过 Git 提交完整还原的正式版本。

### 3.3 V1 的核心意义

早期阶段最重要的事情通常不是架构复杂度，而是回答：

```
这个想法是否值得继续做？
 ↓
核心功能是什么？
 ↓
用户如何使用？
 ↓
产品交互是否成立？
```

因此，V1 的价值主要体现在：

- 验证产品想法
- 探索核心功能
- 建立最初的交互模型
- 为后续版本积累经验

## 9. Local-First 方向

### 9.1 什么是 Local-First

Local-First（本地优先）是一种应用架构思想：

> 核心数据与核心使用体验优先建立在用户本地，而不是把服务器作为唯一的数据来源。

传统模式可以简单表示为：

```
用户
 ↓
服务器
 ↓
数据库
```

Local-First 更接近：

```
用户设备
 ↓
本地数据
 ↓
本地业务逻辑
```

### 9.2 Local-First 的潜在价值

这种架构可以帮助改善：

- 离线使用
- 本地响应速度
- 数据自主性
- 网络依赖
- 多设备数据同步模型

但 Local-First 并不意味着：

> 完全不需要服务器。

服务器仍然可能承担：

- 信令
- 节点发现
- NAT 穿透辅助
- 中继
- 身份辅助
- 可选同步
- 公共服务

因此更加准确的表述是：

> 服务器从"唯一的数据中心"逐渐转变为"必要时提供辅助能力的基础设施"。

## 10. P2P 方向

### 10.1 什么是 P2P

P2P（Peer-to-Peer）即点对点通信。

传统 Client-Server 模式：

```
A ───► Server ◄─── B
```

P2P 模式：

```
A ◄──────────► B
```

部分通信可以直接发生在参与者之间。

### 10.2 P2P 的潜在意义

P2P 可以用于探索：

- 用户之间直接通信
- 降低中心服务器的数据传输压力
- 减少部分中心化依赖
- 支持更加分布式的数据交换方式

### 10.3 P2P 不等于完全去中心化

需要明确：

> P2P 并不自动意味着完全去中心化。

真实系统仍可能需要：

```
P2P + Signaling + STUN + TURN / Relay + 身份服务
```

等辅助设施。

因此 Nymir 更合理的方向可能是：

> P2P 数据通信 + 服务器辅助基础设施

而不是简单追求"完全没有服务器"。

---

## 11. E2EE 方向

### 11.1 什么是 E2EE

E2EE（End-to-End Encryption，端到端加密）的目标是：

> 让通信内容尽可能只有通信参与者能够解密。

基本过程：

```
发送者
 │
 │ 加密
 ▼
密文
 │
 │ 网络传输
 ▼
接收者
 │
 │ 解密
 ▼
明文
```

### 11.2 E2EE 与其他架构的关系

可以简单理解为：

```
Local-First → 数据优先在哪里？
P2P         → 数据如何在节点之间传输？
E2EE        → 通信内容由谁能够读取？
```

三个概念解决的是不同问题。

### 11.3 E2EE 不等于整个系统天然安全

这是必须明确的。

E2EE 的安全性仍然取决于：

- 密钥生成
- 密钥保存
- 密钥交换
- 身份验证
- 密钥轮换
- 设备管理
- 加密协议
- 消息完整性
- 防重放机制
- 具体代码实现

因此：

> E2EE 是安全架构的一部分，而不是"开启一个功能后整个应用自动安全"。

## 18. 最终总结

Nymir 的项目历史存在一个非常明确的分界点：

> V1 和 V2 属于 GitHub 建仓前的项目历史；V3 开始正式进入 GitHub 版本历史。

因此，在研究 Nymir 的发展过程时，应当同时考虑：

```
项目实际发展历史 + GitHub 可验证历史 + 当前代码实现 + 未来架构规划
```

四者不能混为一谈。

从项目发展的角度来看：

**V1 / V2** 解决的是：

> Nymir 从哪里开始。

**V3** 解决的是：

> Nymir 从什么时候开始形成正式、可追踪的软件项目。

而后续版本解决的是：

> Nymir 应该如何逐渐成为一个更加完整、可靠、可维护的系统。

未来如果继续探索：

```
Local-First + P2P + E2EE
```

那么项目真正面对的挑战将从单纯的功能开发，逐渐转向：

```
数据模型 + 同步 + 身份 + 网络 + 安全 + 工程质量
```

因此，Nymir 下一阶段最重要的并不是单纯增加功能数量，而是：

> 建立能够长期演化、验证和维护的基础架构。
